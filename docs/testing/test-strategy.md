# 测试策略与质量准入

日期：2026-10-24；状态：生产验收拟定基线。
关联：FR-001–FR-008、NFR-001–NFR-007。
实际执行结果见[验证报告](validation-report.md)，需求和门禁见[需求规格](../requirements/system-requirements.md)。

## 1. 目标与边界

证明 Rust/Python 互操作的正常行为、错误语义、引用与线程约束、版本兼容，以及目录和打包路径的完整性。
单台机器通过不等于声明平台全部通过；跳过、仅编译和诊断忽略模式必须单独记录。

测试分为本地相关回归、合并门禁、发行矩阵和发布后验证。
测试负责人维护矩阵，开发负责人处理缺陷，发行负责人依据证据决定交付。

## 2. 分层与入口

| 层级 | 目标和重点 | 代码/工具入口 | 门禁 |
| --- | --- | --- | --- |
| 仓库一致性 | Cargo 相对路径、指南 include、工程文档链接、需求追踪 | `tools/check_repository.py`、Cargo metadata、Nox fmt | G1 |
| 组件单元 | Python 配置解析、宏解析/生成、FFI 条件和内省模型 | `cargo test -p r2p-build-config` 等组件测试 | G2 |
| 主库单元 | 内置类型、转换、错误、引用、容器、同步 | `cargo test -p r2p --lib` | G2 |
| Rust 集成 | 函数、类、继承、GC、buffer、模块、异步和异常 | `tests/*.rs`、`nox -s test-rust` | G2 |
| 编译诊断 | 非法声明被拒绝，错误内容可理解且稳定 | `tests/test_compile_error.rs`、`tests/ui/` | G2 |
| 文档示例 | API 示例和指南可编译/执行 | `cargo test -p r2p --doc --features full` | G2 |
| Python 行为 | wheel 构建/安装/导入，参数、异常、枚举、并发、终结 | `tests/python/noxfile.py` | G3 |
| 类型与内省 | stub 与二进制一致，受支持格式解析和错误处理 | `nox -s test-introspection` | G3/G4 |
| 消费方示例 | maturin、setuptools-rust、Meson、嵌入、FFI 示例 | `nox -s test-py`、`examples/` | G3 |
| 底层对照 | FFI 签名、常量、布局与对应 Python 头文件一致 | `nox -s ffi-check` | G4 |
| 性能 | 同条件基准比较、退化归因 | `benchmarks/r2p-benches/` | G4 |
| 制品和恢复 | 内容、哈希、隔离安装、固定旧版本恢复 | 发行记录和回退演练 | G5/G6 |

Nox 是完整矩阵的统一入口，单独 Cargo 命令用于有明确范围的回归。
命令及依赖见[开发指南](../development/developer-guide.md)。

## 4. 兼容矩阵

| 维度 | 验证要求 |
| --- | --- |
| Rust | MSRV 1.85、stable 必需；beta/nightly 为前瞻，失败需分类 |
| CPython | 3.9–3.15 的已声明组合；3.14t/3.15t 单独列 free-threaded 行 |
| PyPy/GraalPy | 分别构建和运行扩展；无嵌入 API 的场景仅编译并明确限制；GraalPy 范围差异待决策 |
| 操作系统/架构 | 以 CI 配置和首期支持决策为准；Linux、macOS、Windows 与架构分别记录 |
| 特性 | 默认、无默认、full、abi3、abi3 最低版本兼容、multiple-pymethods、实验组合按 Nox 枚举 |
| ABI/GIL | CPython 原生、Limited API、free-threaded、abi3t 分开；不能跨组复用结论 |
| 平台扩展 | WASI/Emscripten、交叉编译和 WIP no_std 有专门构建与执行条件 |

矩阵行至少包含 SHA、OS/架构、Rust、解释器、GIL、ABI、features、命令、结果、日志和例外。
实际声明范围见[接口与兼容性](../architecture/interfaces-and-compatibility.md)；未执行的行标为“未验证”，不能填“通过”。

`UI_TEST=ignore` 仅覆盖编译执行，不能证明诊断快照通过；`UI_TEST=skip` 完全跳过。
stable 的正式 G2 需要默认严格诊断模式。
不要为通过本地新工具链而无审核批量重写快照。

## 5. 数据与环境

单元/集成使用仓库构造对象；属性测试记录随机种子和可复现最小输入。
无需业务数据库或真实用户数据。
Python 可选依赖没有可用 wheel 时，相关跳过项随报告列出。

构建环境应固定工具链、解释器和依赖解析。
开发缓存用于效率；发行制品另在隔离环境验证。
扩展构建变量与嵌入链接变量分别管理，防止测试污染。
资源、二进制和内省夹具保留来源，不将本地虚拟环境、缓存或机器路径提交。

## 6. 缺陷与停止条件

按可复现性、影响平台、API/ABI 影响及用户损失分类。
崩溃、潜在内存错误、错误制品/ABI、不可导入和关键语义回归为发行阻断。
格式、链接、诊断和非必需前瞻工具链问题也需记录，不能合并到“环境原因”笼统关闭。

缺陷记录包含版本、环境、最小复现、期望/实际、日志、影响、负责人、修复和回归证据。
修复后重跑受影响层及相邻边界；没有新变化或失败证据时不重复全量测试。

## 7. 退出与交付

G1–G3 的所有必需项成功且阻断缺陷清零后，进入兼容与发行验收。
G4–G6 还需完整支持矩阵、性能决策、来源与制品验证、责任分配及恢复演练。

报告分别给出已通过、已失败、跳过、未执行和待确认，不用总分掩盖 P0 失败。
批准记录应引用具体 SHA 和报告；批准失效条件为源码、依赖、构建配置或目标平台发生变化。
