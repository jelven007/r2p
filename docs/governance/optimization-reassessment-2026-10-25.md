## 1. 当前判断

r2p 已有较完整的 SDK 内核和本地工程验收，下一阶段最有价值的投入是最终交付验证、证据准确性、持续发行能力和维护成本控制。
本地候选成功、远端完整成功、公开制品可用应各自有实际证据。
目前本机候选来源为 `9bdbaeba`，性能候选来源为 `ba53c8a1`，当前 HEAD 为 `643b3204`；这些结果不能自动升级为最终 HEAD 的全部验收。

建议继续保留安全对象层、FFI、宏、构建配置的现有边界。
优先完成最终 SHA 的完整 CI、候选制品和源码合并，再按数据推进性能与核心模块改动。
独立 Python runtime 尚无明确功能，维持预留状态；SDK 扩展、Rust 嵌入和内省 CLI 是已经存在的消费链路。

## 3. 当前缺口与影响

### 3.1 最终交付证据尚未汇合

本地七个提交仍未推送；此数量基于本地跟踪引用，不是本轮远端查询结果。
候选包验收 SHA 为 9bdbaeba，最终 HEAD 尚无完整 CI 和七平台 wheel 结果。
最近完整 CI 40150316493 共 91 个任务，engineering 和 Windows GraalPy 安装路径失败，conclusion 正确阻断。
本地已有相应修复，尚待新 SHA 复验；见[解释器绑定报告](../testing/reports/ci-interpreter-binding-2026-10-25.md)。

该分支含 build.yml 修改，当前选择模型会触发完整矩阵。
完成最终提交后应运行同 SHA 候选验收和完整 CI，再调度 CLI wheel 工作流；不能用本机旧候选或旧 CI 作为新 SHA 的成功 gate。
源码交付关闭时核验合并提交、本地/远端 main 和两个历史标签。
若要在合并提交上发行，还需要该合并 SHA 的完整验证；本分支 CI 入口目前没有普通 main push 触发器。

### 3.2 实际 GIL 状态可能被证据导入误标

`tools/engineering/environment.py` 的探针只记录编译配置 `Py_GIL_DISABLED`。
`tools/evidence.py` 的 import_local 用该字段直接推导 GIL enabled/disabled；它表达的是解释器是否采用 free-threaded 构建，不能完全代表当前进程是否开启 GIL。

本轮使用 CPython 3.14.9t 并设置 `PYTHON_GIL=1`：

| 字段 | 实际结果 |
| --- | --- |
| Py_GIL_DISABLED / free_threaded | true |
| sys._is_gil_enabled() | true |
| 当前 import_local 推导标签 | disabled |

这是已复现的证据准确性问题，尚未在本轮修改代码。
应分别记录 free-threaded 构建与实际 GIL 状态，并处理旧 Python 无该接口、模块导入后 GIL 状态变化以及未记录的旧证据。
import_actions 还从任务名推导版本、GIL 和 run 等级，应改为使用实际环境和步骤结果；安装失败不提供 SDK 行为证据。
已有性能探针另外校验实际运行 GIL，不能将本问题直接解释为既有性能样本失效。

### 3.3 候选流程固定在首次 0.30.0 验收

`tools/candidate.py` 和 `candidate_artifacts.py` 均要求 candidate 与 baseline 版本为 0.30.0。
这符合已经完成的首次契约，但无法直接用于 0.30.1 或后续升级到新版本再恢复旧版本的持续发行。
下一版本需要从各自完整 SHA 读取版本，校验每组内部精确依赖，并允许候选与恢复版本不同。
SDK 六包集合、消费者样例版本和 Python CLI 分发版本应分别有明确规则。

自定义 `publish_candidate.py` 已验证上传请求体保留原始 crate 字节；公开 API、索引可见性、部分成功后的续发/停止尚未实测。
首次外部发行前还需真实 namespace 授权、每包上传结果与下载摘要、索引等待、失败恢复和审核记录。
本地 sparse 注册表不提供这些外部运营证据。

### 3.4 平台与发布政策仍存在重复来源

构建 10/45 矩阵已集中到 `engineering/ci_matrix.py`，这是已完成的改善。
Clippy 目标在 CI YAML 和 release_gate 中各有一份；内省、跨编译及七平台 CLI 集合也跨 YAML/Python 重复维护。
前瞻例外部分由固定任务名字符串判断。
当前一致不保证未来扩展不会出现“工作流运行了，但发布 gate 找不到正确任务”的维护故障。

建议为每个组合定义稳定 ID、runner、架构、工具链、解释器、支持等级与允许结果。
由该配置生成执行矩阵与 gate 必需集合，并验证增删平台、MSRV 变化和前瞻例外。
稳定汇总与细粒度发布检查继续保留。

### 3.5 当前入口、需求与证据索引有漂移

README 的“最新验证”仍主要指向生产基线报告，目录将 python/ 简称为独立 runtime 包。
runtime 实际只有版本常量与占位 README，pyproject 却仍标记 Beta；应明确预留状态和禁止发行范围。
tools/README.md 尚未列出候选、发布 gate、CLI wheel 验收、性能采样和上游同步等新工具。

追踪矩阵的 NFR-002/NFR-007 仍使用 not-collected，实际已采集性能样本和本地候选恢复。
应记录“样本已采集、门限待校准”和“本地恢复通过、外部恢复待验收”，不能把相应需求直接标为全部通过。
27 条结构化记录目前全部为 success；最近失败 CI 已在报告中记录，但尚未导入机器证据。
应允许失败、配置、编译、运行和交付结果完整关联，并区分调查触发阈值与正式性能阻断门限。
本地路径检查通过不能发现上述语义漂移。

### 3.6 工具规模增加，需要控制职责与临时资源

Nox 仍为 2,204 行，含 Rust/Python、文档站点、跨编译、FFI、内省等职责。
已有纯参数与矩阵模块抽取应保留，再按影响逐步迁移文档、打包和平台辅助函数。
无需用文件行数驱动一次性搬迁核心代码。

候选、CLI 和 MSRV 工具会保留临时目录、Cargo home 与 worktree。
保留失败现场有价值，但成功后也应明确哪些制品需要长期保存、哪些可清理。
现有发布/恢复依赖 target 中的原始字节或 CI artifact；需要明确保留期限、取回验证和到期处理。
清理临时数据不能删除最后已验收的恢复制品或移动历史标签。

### 3.7 性能与支持投入需要真实数据

GIL 模式的候选最小探针 clean 中位数为 25.29 秒，full 为 48.60 秒；这提示按需 feature 有编译成本收益，不能外推为任意业务二进制或运行时加速。
free-threaded 四线程调用的候选/基线中位数差为 +139.6%，候选 CV 为 32%，基线 CV 为 41.1%；应优先复测和控制环境，不能直接归因于 ReferencePool。
当前线程数增加时总工作量也增加，下次需同时测固定总工作量与固定每线程工作量。

应在真实扩展/嵌入负载下测吞吐、单位成本、RSS、转换/复制和编译成本。
先优化必要特性、边界调用次数和批量处理，再决定是否修改内核同步。
CI 分流改善尚无连续 20 次成本样本，不能声称已满足五分钟目标或给出稳定节省比例。

最近记录中 main 未保护，私密漏洞报告启用返回 403，维护责任集中在一人且无备份。
Issues 已启用；真实外部首次集成、升级、反馈和响应指标尚未采集。
应优先落实渠道、维护窗口和真实试用项目，再确定支持期限与响应承诺。

## 5. 推荐执行顺序

1. **关闭本轮交付**：固定最终 SHA，补齐完整 CI、候选和 CLI wheel，保留真实失败并修到成功，再核验源码交付。
2. **修正证据与当前入口**：处理 GIL 复现、环境/步骤分级、当前与历史索引以及已采集数据的准确状态。
3. **形成持续发行能力**：参数化版本、统一平台政策、管理原始制品保留，验证跨版本恢复。
4. **开展受控试用**：选一个 Python 扩展和一个 Rust 嵌入项目，记录首次集成、升级、错误处理与反馈；此为试用目标，不是已有外部样本。
5. **按测量实施后续优化**：先改善调用方式、feature 选择和工程成本，再决定内核改动；同步相关 GC、重入、释放、终结和 FT 回归。
