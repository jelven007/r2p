# 文档治理与变更管理

版本：2.0；日期：2026-10-24；状态：当前工程规范。
关联：FR-008、NFR-006。

根 README 和入口文件引用唯一来源，不重复维护整套规格。

## 2. 状态、版本和证据

每份工程文档写明日期、适用范围和状态。
状态语言遵循[文档中心](../README.md)：已实现、已落地、工程规范、发行准入要求、待确认和已验证。
需求状态与能力状态分开，文档存在不等于需求已验收。

稳定编号为 FR/NFR、G、ADR、Q、WP、R；删除或废弃保留历史记录，不能将已有编号重新用于其他含义。
CSV 中的 source/design/test_evidence 是文件引用，acceptance_gate 引用已定义门禁。

Git 保存文档变更；发布/测试报告额外记录源码 SHA、环境、命令、结果和制品。
日期不能代替版本；工作区有未提交修改时说明“基于 SHA 的本地变更”，不把 HEAD 当成已包含全部修改。

## 3. 同步触发规则

| 变更 | 同步更新 |
| --- | --- |
| 公共 API、异常、转换、线程/生命周期 | 接口、用户指南、需求追踪、相关回归和发行说明 |
| Python/MSRV/ABI/特性支持 | 清单、构建配置、Nox/CI、兼容矩阵、测试和支持政策 |
| 目录/包身份/构建打包 | 目录映射、ADR、依赖和工具路径、开发/运维/发行资料 |
| 新需求或范围 | 需求规格、追踪矩阵、方案、计划、验收与运营影响 |
| 缺陷或事故 | 最小复现、根因、回归、已知问题、恢复及预防任务 |
| 发行 | 版本/变更说明、矩阵报告、制品/哈希、支持状态和恢复记录 |

开发者在同一变更中更新受影响材料；审阅者检查代码与文档是否一致。
只做文案修改时运行文档检查；路径和行为变更同时运行相应构建/回归。

## 4. 检查与审阅

`tools/check_repository.py` 检查 Cargo 路径、工程链接、指南 include、主库 doctest、需求追踪、SDK/产品身份、两个快照及 SHA。
Nox `fmt` 包含 `repository-check`，Markdown 格式使用 `rumdl`。
用户指南的外链和锚点由 `check-guide` 及人工审阅补充。

自动检查不能证明需求合理、ADR正确、命令有授权或平台已通过。
审阅重点：状态和证据一致、路径真实、矩阵例外可见、产品/上游边界明确、负责人和验收可执行。

范围、支持承诺、独立发行身份和运行预算需要相应负责人确认；常规目录/文档维护按已有任务授权执行。
本次核验 GitHub main 未配置分支保护；PR 工作流与本地核验不能描述为已启用强制平台控制。

## 5. 归档和周期维护

保留上游快照原文，其相对链接和历史命令仅供参考。
上游升级时新建带版本的参考快照或记录变更来源，不无记录覆盖本次基线。
生成的 Rustdoc、mdBook 和测试缓存不提交为文档源。

每次发行复核需求、矩阵、支持与回退资料；每月复核运营/运维内容和未决事项。
发现失效命令或链接时建立任务并修复唯一来源。
真实负责人、保存位置和保留期在生产准入时补齐。

变更/测试/发行/事故记录使用[记录模板](change-record-template.md)，并按[交付计划](delivery-plan.md)关闭工作包。
历史报告的命令/结果保持当时语义，目录移动只调整导航；新阶段结果创建新报告，不把旧范围改写为新结论。
