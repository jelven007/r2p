## 1. 核心判断

当前最有价值的优化是明确产品责任、修正质量门禁、建立可追溯的真实制品交付，并证明目标平台可用。
进一步移动目录或大规模拆分核心库的边际收益已经较低。

r2p 的源码能力和上游工程体系较完整，本仓库已经建立职责目录和生命周期文档，但独立产品、完整验收、发行身份与支持机制仍未完成。
现状应表述为“可继续研发的 SDK 工程基线”，不能据此宣称已具备业务生产系统。

分析发现的 MSRV 特性任务与结果汇总问题继承自拉取基线，并非目录移动导致。
两项配置已本地修正，实际工具链选择、MSRV 编译和汇总回归结果见[CI 修正验证](../testing/reports/ci-fixes-validation.md)。
其他条目仍为建议；没有执行远端 CI、性能测量或完整代码安全审计。

## 4. 产品、架构和目录建议

### OPT-01：先确定本仓库的产品

当前产品身份为 `r2p`，见[ADR-0002](../architecture/adr/0002-product-and-release-boundaries.md)。
根 [Cargo.toml](../../Cargo.toml) 的包名已迁移为 `r2p`，版本声明为 `0.30.0`，repository 和 homepage 已指向本仓库，PyO3 作者与版权保留。
目前没有业务 API、数据库模型或业务应用。

| 路线 | 适用目标 | 建议架构与维护方式 |
| --- | --- | --- |
| SDK 定制 | 需要改变 FFI、宏、解释器兼容或核心语义 | 保持核心架构，维护最小补丁与上游跟踪；完整承担 ABI/MSRV 回归 |
| 业务生产系统 | 需要提供具体用户功能、业务流程和数据处理 | 在稳定 r2p 之上建立业务模块和少量语言适配层；通过依赖消费 SDK |
| 内部验证平台 | 比较或验证 r2p/解释器能力 | 固定 revision、记录环境和结果，明确实验范围，不默认公开发行 |

若目标是业务系统，优先定义用户、输入/输出、错误、数据与部署，再确定是否需要服务进程。
没有独立需求时，不增加微服务、数据库、消息队列或 Kubernetes 作为目录装饰。

独立发行还要协调 crate 名称、精确版本依赖、宏生成路径、Python 包、元数据和文档目标。
避免仅修改一个包名就发布；决策规则见[ADR-0002](../architecture/adr/0002-product-and-release-boundaries.md)。

### OPT-06：当前目录合理，但要管理同步成本

`src/`、`crates/`、`tests/`、`tools/`、`benchmarks/`、`docs/` 等组织适合 SDK 工程，根 Rust 集成测试保留也是正确选择。
354 个文件的迁移同时使本仓库与上游路径产生持续差异。

建议保留未改写的上游跟踪分支，使用单独同步分支处理来源升级、目录映射和本仓库补丁。
将目录重构、产品文档和功能补丁分别组织为可审阅的逻辑提交，不合并成一个难以回溯的大提交。
记录每次上游 SHA、冲突、被保留/替换的补丁和回归证据。

如果主要目标只是消费 r2p 且需要频繁升级，评估将业务产品放入独立仓库或适配层，通过受控依赖使用 r2p 的方案。
无需现在推翻已经验证的目录，先用一次真实同步衡量成本。

核心库的 FFI/宏/对象层边界可以保留。
新业务避免依赖 `src/impl_` 等内部模块；它们服务代码生成和内部实现，变化会扩大产品维护成本。

## 5. CI、测试和兼容建议

### OPT-02：MSRV 特性任务的原问题与修正

拉取基线的 `check-feature-powerset` 定义 stable/MSRV 两项，却对两项都安装并选用 stable。
MSRV 项只追加 `minimal-versions`；[Nox](../../noxfile.py) 的 `check_feature_powerset` 只是选择 cargo 子命令，没有切换 Rust 工具链。

原配置不能作为“全部声明特性在 Rust 1.85 下可编译”的证据。
仓库另外已有真实 `check-msrv` 和 build 矩阵，本问题不意味着所有 MSRV 验证均缺失。

当前[ci.yml](../../.github/workflows/ci.yml) 通过 job 级 `RUSTUP_TOOLCHAIN` 绑定 `matrix.rust`，先安装/输出版本，再恢复缓存。
本机执行该安装步骤时分别得到 Rust 1.99.1 和 1.85.1，兼容依赖解析后的 MSRV full/all-targets 编译通过。
完整 CI powerset、最低依赖与 Python 3.15 组合仍需远端运行，见[验证范围](../testing/reports/ci-fixes-validation.md)。

### OPT-03：原汇总遗漏与当前门禁

拉取基线的 `conclusion.needs` 没有包含：

- `pytests-type-checking`；
- `test-introspection-pr`；
- `test-debug-min-version`；
- `semver-checks`。

原 `resolve` 也未直接列入，但多项已列入的任务依赖它，不应将所有未直接列项一概视为遗漏。

若分支规则只要求 `conclusion`，原配置中的上述测试失败不能由汇总任务本身阻断。
实际远端分支保护可能另有要求，目前没有读取证据，不能断言本仓库已存在合并绕过。

当前汇总补齐四个任务并显式加入 `resolve`，覆盖全部 24 个前置任务。
50 个成功/跳过/失败/取消执行场景通过，8 个原配置放行的遗漏任务回归场景已被阻断。
原事件条件和跳过策略保留；远端 required checks 的对齐、必需任务被错误跳过的进一步治理仍待完成。

### OPT-05：用真实矩阵治理兼容承诺

FFI 元数据已经被 Nox 使用，应继续作为解释器声明的来源。
在其上维护 r2p 正式承诺的子集和对应证据，避免再维护一份互相漂移的版本清单。

GraalPy 元数据为 Python 3.12–3.13，README/CI 口径指向 25.4/3.13，需通过目标需求和运行测试统一。
CPython 原生、abi3、free-threaded、abi3t、PyPy/GraalPy、WASI/Emscripten 分开列配置。

每行记录 SHA、Rust、Python 实现/版本、OS/架构、ABI/GIL、features、命令、结果与日志。
声明的正式范围可以小于上游配置范围；缩小承诺需明确消费方和迁移影响。
保留本仓库完整测试能力，在必需 PR 检查、完整合并/候选检查和前瞻任务之间分配运行频率。
是否减少 CI 任务先依据运行时长、失败率、消费平台和费用，不直接删掉关键覆盖。

### OPT-09：把验收对象从“文件”细化到“行为”

现有 `traceability.csv` 给每条需求连接实现、方案和测试文件，是定位索引。
它不能证明某个输入边界、错误语义、ABI 或平台已通过。

建议为关键用例配置稳定 ID，关联正常输入、边界、错误、线程、版本以及期望结果。
结果由测试工具导出并连接需求和矩阵，不手工复制全部日志。
对本次 110 个 ignored 和 7 个条件过滤按原因/适用条件管理，不要求机械清零，也不把它们计为通过。

Valgrind、careful、FFI 对照、semver 检查已有自动化，优先取得并保存本仓库实际结果。
unsafe/线程变化增加针对生命周期、GC、临界区和并发的回归；复杂故障先采集运行证据。
仅凭 unsafe 数量或文件行数不能判断存在漏洞。

## 6. 工具、实验能力和性能建议

### OPT-07：工程环境和目标解释器分开表达

工程 dev 组需要 Python 3.14，SDK 声明支持 Python 3.9 起。
仓库没有 `.python-version` 或 Rust 工具链固定文件；CI 指定了工程 Python，普通本地入口仍受安装环境影响。
本次也经历过 Xcode Python 缺链接库和 uv 同环境同步移除启动器的问题。

建议固定工程工具 Python，提供一个入口分别接受工具链和目标解释器，并在日志首部输出实际配置。
工程 uv 在项目虚拟环境之外安装；SDK 测试仍需运行在相应目标解释器，不能把 Nox 的 `sys.version_info` 固定为工具 Python 后误测其他版本。
Rust 开发复现保存已验证工具链，同时继续周期检查最新 stable/MSRV；不把全套兼容 CI 全部改成一个固定版本。

### OPT-08：模块化 Nox，保留对外会话接口

当前 `noxfile.py` 为 2139 行，包含编译、Python、兼容、FFI、基准、文档和站点构建。
建议将内部实现组织到 `tools/nox/`，例如 compatibility、rust、python、docs、packaging 模块，根 noxfile 保留会话注册和原参数。

兼容元数据、路径常量和公共命令封装统一维护。
先拆内部帮助函数，再按职责迁移会话；避免一次同时改会话名称、路径和测试策略。
验证会话列表、参数转发、工作目录、环境以及代表性运行结果。

### OPT-10：实验能力需要单独的产品承诺

`experimental-async`、`experimental-inspect` 和 WIP no_std 不应因为进入 `full` 测试集合而获得稳定承诺。
内省已经支持 ELF/Mach-O/PE，应进一步验证无效/截断二进制、剥离和多架构、协议版本及输出兼容。
只有格式/解析边界需要时增加针对性模糊测试。

`python/r2p-runtime` 的源码当前仅有 `__version__ = "0.0.1"`，README 为 `Coming soon!`。
其 sdist/wheel 和导入验证证明打包链路可用，不证明已经具备运行时功能。
建议将它明确为预留/实验包，先定义功能和调用方，再决定正式发行与支持。

### OPT-12：按真实场景优化性能和编译成本

已有 21 个 Rust 基准和 CodSpeed 工作流。
当前该工作流使用 CPython `3.14t` 和 simulation 模式；补充实际消费方所用的 GIL/ABI 条件和真实耗时/内存结果。

优先测量小调用次数、转换/复制、附着/释放、容器遍历与并发竞争。
验证批量接口、Rust 内循环、可安全借用的 buffer、合适的 `detach` 和按需特性是否改善目标场景。
先证明正确性与收益，再应用具体优化，不省略引用或同步检查换取结果。

分别记录增量/干净构建时长、二进制大小和运行性能。
生产消费方选择必要 features；`full` 是测试集合，没有必要成为所有产品的默认依赖配置。
拟定 5% 退化阈值需要结合样本波动和真实使用场景校准。

## 7. 制品、供应链、运营与文档建议

### OPT-04：从测试源码走到可验证制品

[release.yml](../../.github/workflows/release.yml) 在 `v*` 标签或手动事件下直接执行 workspace publish，工作流本身没有核验目标 SHA 对应的完整质量结果。
`environment: release` 可能提供额外审批，但其远端配置未核验。
发布前应绑定同一 SHA 的验收证据，核验名称、版本、平台标签、依赖及制品哈希。

已有 Python attestation 和 OIDC 应保留。
正式发布使用已经验收的构建结果；必须重新构建时记录环境并再次验证，不能假定同标签的新构建等同于候选制品。

本次发现的许可证链接问题说明需要持续的 package smoke 门禁。
建议将 sdist→wheel→隔离安装/导入、Rust 候选依赖链打包/编译及必要文件/许可检查纳入 CI。
`cargo package --list` 与 `cargo package` verification 使用不同状态，前者不能替代后者。
确切依赖版本未在目标注册表可用时，需要先确定候选包/内部注册表链路。

### OPT-14：补齐已存在控制的运营证据

Actions SHA 固定、OIDC、Dependabot 和 zizmor 已有，继续使用。
发行保存 Rust 依赖解析快照、工具版本和来源；库的 Cargo.lock 策略与应用/发行锁定策略分别决定。
事实更正：根 Cargo.lock 已跟踪；仅新增子工作区锁文件按忽略规则处理。
每次发行保存实际依赖解析，MSRV 兼容解析在隔离副本执行。

本仓库缺少 `SECURITY.md` 和 `.github/CODEOWNERS`。
有实际人员和响应渠道后配置职责与问题报告政策，并核验远端环境、分支/标签规则、注册表身份和支持周期。
这不是发现了可利用漏洞，而是独立维护所需的责任和证据工作。

后续生产工程整理采用 `./.github/` 相对引用，以保持现有工作流检查工具和运行配置一致。
面向旧 runner 或 GitHub Enterprise Server 时另外核验适用性，参考[GitHub 官方文档](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/write-workflows/choose-what-workflows-do/find-and-customize-actions)。

### OPT-11：让支持与恢复流程有真实归属

该历史缺口已在生产工程整理中修正为本仓库文档与支持政策。
目标 fork 仓库 Issues 关闭，当前授权不能改设置；使用复现/修复 PR 反馈，不称上游社区为本仓库支持。
站点构建已使用 r2p 路由，可通过 `R2P_GUIDE_ARCHIVE` 显式纳入产品版本指南，`R2P_SITE_URL` 配置 canonical 地址。
选择独立产品路线后，应区分本仓库支持入口、源码问题和上游参考资料。
不能把官方社区和站点作为已经由 r2p 承担的服务资产。

首期只建立必要指标：消费项目/版本、按平台的构建或导入失败、问题响应、修复时长和复发情况。
不默认加入 SDK 使用遥测，也不套用业务服务 QPS/数据库 RPO。
至少完成一次固定旧制品安装及目标站点静态制品恢复演练，记录实际负责人和结果。

### OPT-13：文档检查再向结构化契约推进

当前检查覆盖本地路径、指南 include、doctest、需求 ID/文件引用和许可证。
未校验 Markdown 锚点、外网链接、全部 CI/Nox 路径、模板有效性或真实验收语义。

建议补充必需文档清单、Markdown 解析/锚点检查、支持矩阵一致性、包资源规则，以及受维护范围的工作流语法检查。
选择支持当前 GitHub 语法的工具，避免旧 linter 报告新语法为错误。
以缺文档、断链接、缺许可证、错误矩阵和坏制品等负向案例验证检查效果。

保持现有需求/方案/目录/结果各自唯一来源。
实际责任人确定后按阶段维护材料，防止文档数量增长而执行证据仍停留在本次本机报告。
