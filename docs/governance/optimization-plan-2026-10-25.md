# r2p 当前项目分析与优化方案

评估日期：2026-10-25；状态：已确认，按[实施记录](optimization-execution-2026-10-25.md)推进。
评估基线：`3a24917eb2766aa8ded8c04fefde1c1d4b133c00`，本地与 GitHub main 一致。
范围：SDK 架构、消费入口、构建配置、测试与 CI、制品交付、性能、上游维护、文档和运营。
本文件更新下一阶段的工作建议，不改写[既有交付事实](../releases/records/2026-10-24-production-baseline.md)。

## 1. 判断与推荐方向

r2p 已经形成可继续维护的 Rust/Python SDK 工程基线：内核身份统一、组件分层明确、源码交付已闭环，并有跨平台 PR 测试证据。
下一阶段的主要收益来自消费方可重复集成、开发命令可信、测试门禁可执行、CI 成本可控和上游持续维护。
保留当前 `src/`、`crates/`、`tests/` 等职责边界，按实际变更热点逐步整理内部实现。

建议先交付一个小迭代：修复快速测试入口，提供仓库外可用的源码模板，分流工程文档 CI，并同步实际支持渠道。
随后加强矩阵选择与制品准入，再依据测量决定运行时优化。

产品优先覆盖两条已有链路：

1. Python 项目通过 r2p 构建 Rust 扩展，安装 wheel 并调用函数/类。
2. Rust 应用通过 r2p 嵌入或调用 Python，管理异常、线程附着和对象生命周期。

`experimental-async`、内省、WIP no_std、abi3t 分别管理实验范围。
`python/r2p-runtime` 当前只有版本常量和占位说明，不能列为已实现的独立运行时产品。

## 3. 架构分析与优化边界

| 层级 | 主要入口 | 职责 | 优化方向 |
| --- | --- | --- | --- |
| 安全 API 与对象模型 | `src/instance.rs`、`marker.rs`、`conversion.rs`、`types/` | Py、Bound、Borrowed、转换与 Python API | 保持公开 API 稳定，优先改善用法与诊断 |
| 生命周期与同步 | `src/internal/state.rs`、`interpreter_lifecycle.rs`、`sync/` | 附着/分离、初始化、延迟释放、临界区 | 用并发/终结回归和真实测量驱动变更 |
| FFI | `crates/r2p-ffi` | 符号、内存布局、版本/ABI 条件 | 坚持头文件对照和平台运行验证 |
| 编译期配置 | `crates/r2p-build-config` | 解释器发现、环境优先级、链接和 cfg | 结构化配置诊断，降低环境误用 |
| 过程宏 | `r2p-macros`、`r2p-macros-backend` | 声明解析、Rust 胶水生成和错误诊断 | 保持薄入口，按解析/模型/生成/诊断组织 |
| 实验内省 | `crates/r2p-introspection` | ELF/Mach-O/PE 元数据解析与 stub | 增加异常输入和资源边界测试 |
| 消费适配与工程工具 | `tools/maturin-bridge`、examples、Nox | 打包兼容、样例、矩阵编排 | 仓库外验收、显式参数和统一配置 |

安全对象层依赖 FFI；过程宏生成调用这些 API 的胶水，构建配置决定解释器/ABI/链接条件。
当前分层适合 SDK 工程，没有充分证据支持整体重写。

线程附着不等于 free-threaded 下的数据互斥。
`ReferencePool` 已采用 dirty 原子标记和 Mutex，并在释放锁后执行实际 decref；这包含性能与重入正确性的折中。
只有测量证明竞争是瓶颈，且生命周期/GC 回归通过后，才考虑分片或批量策略。

### O-01：快速模式参数没有生效

**证据：** [README](../../README.md)和[开发指南](../development/developer-guide.md)推荐 `nox -s test-rust -- skip-full`。
但 `_get_feature_sets` 固定生成包含 full 的组合，`_run_cargo_test` 的参数分支只识别 careful/release，没有处理 skip-full。
位置：[noxfile.py:1936](../../noxfile.py#L1936)、[noxfile.py:2048](../../noxfile.py#L2048)。

本次用 AST 载入实际 `test_rust`、`_get_feature_sets`、`_run_cargo_test` 函数，捕获命令而不执行 Cargo。
在 CPython 3.14、非 free-threaded、stable、默认目标条件下，普通模式和 skip-full 均生成 11 条命令，逐项相同，其中 3 条仍含 full。
这是已复现的命令契约问题。

**方案：** 显式解析测试范围，优先兼容已公开的 skip-full 拼写；区分组件冒烟、默认/无默认、full、ABI、严格 UI。
为未知参数提供错误而非静默忽略，并同步开发文档。
“完整”仍使用现有 Nox 矩阵，不借优化入口减少 CI 核心覆盖。

**验收：** 命令生成测试证明快速与完整模式不同，快速模式不含 full；未知参数非零退出；各模式至少运行一组真实回归。

### O-02：源码交付与生成模板采用不同依赖渠道

**证据：** `product.toml` 指定 git-revision，SDK 入门使用 path；Maturin 模板仍为 `r2p = "{{R2P_VERSION}}"`，模板内适配器也从注册表获取 r2p-ffi。
位置：[模板](../../examples/maturin-starter/.template/Cargo.toml#L11)、[模板适配器](../../examples/maturin-starter/.template/maturin-bridge/Cargo.toml)、[迁移说明](../development/kernel-namespace-migration.md)。
迁移说明已承认模板注册表路径需等正式发行；仓库内 path 样例通过不能证明模板生成后可独立构建。

**方案：** 模板支持明确的 source mode：Git revision、已有本地 checkout、未来已验证的注册表版本。
默认采用当前交付渠道，SDK 与私有 Maturin 适配器固定相同来源和 SHA。
建立一条“生成项目 → 新虚拟环境 → sdist/wheel → 独立目录安装 → 导入/行为”的消费方冒烟链路。
适配器的包名是 Maturin 协议要求，继续保持私有，不再机械替换。

**验收：** 不依赖当前 workspace、隐含 patch 或本机绝对路径；依赖图只有一份同源 r2p-ffi；普通 wheel 和 abi3 标签与运行行为一致；生成项目可固定 SHA 重建。
选择两个目标用户的真实最小场景：Python 调 Rust 函数/类，Rust 调 Python 并接收异常。

### O-03：显式环境与可维护的工具组织

**证据：** 工程 dev 组要求 Python 3.14，nox 组未声明相同下限；仓库没有 `.python-version`。
Nox 依据运行它的 `sys.version_info` 和 `sysconfig` 选择受测组合，不能仅固定工具解释器后声称在测其他 Python。
MSRV 会话执行 `cargo update`，当前依靠操作纪律避免覆盖开发锁。
`r2p-build-config/Cargo.toml` 未继承 workspace lints，其他五个 SDK crate 已继承。

**方案：** 提供显式区分“工具 Python”和“目标 Python”的入口，记录实际 executable、实现/版本、Rust、目标 triple、GIL/ABI、特性及配置文件摘要。
工具环境固定到已支持版本，跨解释器会话仍在目标环境运行；MSRV 依赖准备放入隔离副本并保存实际 lock。
给 build-config 补齐适用 lint 契约，例外逐项解释。

Nox 按配置/矩阵、Rust、Python、文档、打包、平台辅助函数渐进拆分。
优先抽取无副作用的配置与矩阵函数；保留 40 个会话名和既有参数，不在一次变更中同时改接口、工作目录和测试选择。

**验收：** 指定目标解释器时执行日志与实际导入一致；MSRV 准备不修改主工作区锁；会话清单、工作目录、参数和目标平台选择前后可比较。

### O-04：CI 减少无关执行与重复排队

**证据：** PR CI 只排除 newsfragments；benches 对全部 PR/main push 运行；CI Cache Warmup 对每次 main push 执行，未设置 concurrency。
benches 的 main 并发组包含 `github.sha`，连续两个提交属于不同组，`cancel-in-progress` 无法相互取消。
位置：[CI 入口](../../.github/workflows/ci.yml#L3)、[基准并发组](../../.github/workflows/benches.yml#L9)、[缓存预热](../../.github/workflows/ci-cache-warmup.yml)。
本次只补六份工程文档也触发了新一轮 main 构建/基准，远端查询可见相邻提交的任务同时存在。

建议按以下变更类型选择检查：

| 变更类型 | 必需执行 | 扩展执行 |
| --- | --- | --- |
| 工程流程文档、治理与运营说明 | 文档格式、路径、追踪与状态检查 | 链接检查按影响执行 |
| SDK README、指南示例和 include | 上述检查、Rustdoc/doctest、指南构建 | 受影响示例 |
| 宏、FFI、对象模型、构建配置、Cargo/锁 | 核心 PR 矩阵、严格 UI、FFI、消费方冒烟 | ABI/解释器/平台完整矩阵按影响选择 |
| 工作流、Nox、打包工具 | 工作流 lint、矩阵选择/汇总正负例、代表性真实执行 | 高影响配置触发更广矩阵 |
| 性能敏感实现与基准 | 相关基准和正确性回归 | 固定环境周期性能比较 |

不要按整个 `docs/` 一刀切跳过 Rust 测试：`docs/sdk` 和 `docs/guide` 含实际编译示例。
main 的可替代缓存预热按工作流/分支串行或取消旧任务；发行和历史证据任务保留单独策略。
耗时安装、下载、编译、测试分别计时，再评估缓存命中和依赖安装优化。

**验收：** 用工程文档、Rustdoc、宏、FFI、锁文件、Nox 六类变更验证任务选择；非预期漏选失败。
提出工程文档检查 ≤5 分钟的试行目标，随后用连续 20 次样本评估 P50/P95、执行分钟、失败/重试率；该目标不是当前实绩。

### O-05：让检查成功对应明确的必需集合

**证据：** 本次确认 `main.protected=false`。
现有汇总已补齐 24 个前置任务，并正确处理失败/取消；但所有 skipped 都可接受，没有进一步判断“这一事件与变更类型本应运行什么”。
完整 powerset 在普通 PR 上不执行，依赖标签、merge_group 或手动触发；当前 CI 没有周期 schedule。
位置：[conclusion](../../.github/workflows/ci.yml#L947)、[powerset](../../.github/workflows/ci.yml#L694)。

**方案：** 矩阵选择先产出 required/optional/not-applicable 集合及理由，汇总只允许有理由的不适用项跳过。
维护者在规则中选择稳定汇总检查，按团队实际审阅条件配置 main 保护；在真实规则生效前不宣称自动强制。
完整兼容矩阵安排周期或候选发行运行，记录成本与异常；前瞻工具链继续与正式支持分开。
同名 r2p 的后续变更恢复 semver 比较，首次包改名的跳过例外不沿用到未来版本。

**验收：** 关键任务失败、取消、意外跳过、矩阵遗漏均能阻断；明确的不适用组合通过；标签/事件变化重新计算 required 集合。
分支规则从远端读取确认；旧的 50 场景汇总回归保留。

### O-06：外部制品发布前补齐同版本验收

**证据：** Rust 发布工作流在开关打开后执行 `cargo publish --workspace`，没有内部绑定必需 CI 结果的步骤。
Python wheel 工作流有 twine 检查和 attestation，但没有逐个 wheel 隔离安装/导入；twine 只验证分发元数据等属性。
既有 Rust `.crate` 证据采用 `--no-verify`，已经如实记录，但不能作为注册表依赖解析和独立安装证明。
位置：[Rust 发布](../../.github/workflows/release.yml)、[wheel 流水线](../../.github/workflows/python-wheel.yml)、[内核验证](../testing/reports/kernel-migration-validation.md)。

**方案：** 候选阶段固定 SHA、包集合、版本、目标矩阵、锁与制品摘要；校验六个 SDK crate 的精确版本关系，确保私有适配器和工程包不在发布集合。
在候选依赖链或明确的隔离注册表环境验证 `.crate`；wheel 在对应解释器/架构的干净环境执行导入与关键行为。
发布只消费已验收清单和制品，绑定来源/审批；重新构建时重新核验哈希与安装结果。

**验收：** 错误标签/版本、缺少依赖、错误 ABI、缺许可证、导入失败均阻断。
下载已发布制品复验；消费方固定旧 SHA/制品可恢复，两个现有历史标签不移动。
首次发行前明确命名空间权限、版本与上游对应关系、支持期限和责任人。

### O-07：将上游演进作为常规维护能力

**证据：** 产品和 SDK 已独立命名，但仍保留 PyO3 核心结构与来源。
大面积包名、生成路径、环境变量和目录差异会增加后续上游修复的移植成本。
仅保存初始上游 SHA 和当前两个快照不足以证明下一次同步可重复。

**方案：** 建立上游提交观察与差异清单，分为身份/目录、打包适配、本地功能、文档四类。
每次同步记录来源 SHA、冲突决策、被替换补丁及回归，不直接覆盖 main。
优先演练一个小的上游修复，再扩展到版本升级。
依赖 PyO3 类型的生态 crate 逐个评估类型/ABI 兼容，不将 Cargo 别名视为适配完成。

**验收：** 一次真实同步能够复现；本地差异有负责人；关键测试通过；迁移说明与版本映射同步。
复杂同步冲突按实际范围重新估算，不能承诺所有上游升级都在本表人日内。

### O-08：性能目标来自真实场景

**证据：** 当前 simulation 基准通过，但 `bench_attach_scaling.rs:103–106` 明确使用 `#[cfg(not(codspeed))]` 排除并发扩展性场景。
`bench_py` 的 custom iterations 也有明确跳过日志。
`ReferencePool` 使用进程级 Mutex，其竞争是否构成真实瓶颈尚无当前消费场景的 walltime 数据。

**方案：** 同时保留 simulation 趋势与真实耗时测量，分开记录 GIL/free-threaded、解释器版本、ABI 和 CPU 条件。
优先测量小调用批量化、字符串/字节转换、容器遍历、附着/分离、延迟释放和 1/2/4/8 线程扩展性。
补充干净/增量编译耗时、峰值内存、制品大小。
先优化调用方式、批量处理和必要特性选择，确认热点后再调整内部算法或同步结构。

**验收：** 基线/候选在同环境至少三次独立运行，保存样本分布、方差与效果量。
5% 退化只能作为待校准阈值，不用于掩盖噪声或不同环境差异。
实际并发场景必须有 walltime 证据，不能用“21 个套件启动成功”替代。

### O-09：把文档状态变成可维护数据

**证据：** 远端 Issues 已开启，当前支持政策仍写关闭；traceability.csv 多处能力状态仍是 local-validated/local-delivered，而远端 PR 已通过并合并。
本地路径检查能证明文件存在，不能发现这种运营或证据状态漂移。
`pyproject.toml` 的 towncrier `issue_format` 仍统一指向 PyO3，未来本仓库新增片段需要独立来源链接。

**方案：** 区分当前状态与历史报告；当前 README/支持政策/资产表统一指向实际入口，历史记录保留当时事实。
支持矩阵维护结构化行：源码 SHA、目标、Rust/Python、GIL/ABI、features、命令、结果、跳过理由、日志 URL、核验时间。
从结构化证据生成摘要，需求“实现状态”和“验收状态”分列。
为新增 r2p 发行片段定义来源，不重写已有上游 CHANGELOG。
落实组件责任人、Issue 分类与首轮响应流程，SLA 在人员与数据具备后决定。
当前没有 `SECURITY.md` 和 `.github/CODEOWNERS`；确定真实维护人员后建立职责映射和适合该仓库能力的私密漏洞报告渠道。
保持 Actions 固定 SHA、依赖更新和发布来源证明，并按实际维护能力安排依赖漏洞检查；这些治理动作不代表本次发现了可利用漏洞。

**验收：** 同一事实只有一个当前来源；有新运行结果时摘要可更新；历史结论不被回填为新状态。
有真实消费方的首次集成、升级和反馈样本；没有数据的指标标记未采集。

### O-10：投入明确边界的鲁棒性验证

**证据：** 内省入口读取整个二进制文件，解析 chunk，并递归组织模块。
现有实现包含长度、偏移、格式版本和格式错误检查，且已有正常/stripped/fat 二进制和 stub 集成验证。
本次未看到统一文件/结构预算或专门异常输入测试目录；这属于进一步验证方向，不是已证明的可利用漏洞。
位置：[introspection.rs](../../crates/r2p-introspection/src/introspection.rs#L533)。

**方案：** 补充截断文件、长度/偏移边界、未知版本、重复 ID、循环/深层关系和超大输入；对纯解析函数设置可测试的资源边界，开展有限范围模糊测试。
核心路径继续利用已有 GC、终结、借用、线程和异常测试，按改动运行 sanitizer/Valgrind 等适用检查。
unsafe 数量和源码行数只用于定位审阅范围，不据此判定漏洞或要求批量重写。

**验收：** 无效输入返回确定错误，资源消耗有界；正常三种二进制格式和 stub 输出保持一致。
运行时优化必须通过重入、引用释放、GC 遍历、终结与 free-threaded 的相关回归。
