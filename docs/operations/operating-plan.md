# r2p 产品运营与支持计划

版本：2.0；日期：2026-10-24；状态：当前源码运营流程；实际采用和响应数据尚未采集。
关联：FR-007、NFR-008。

## 1. 运营对象和目标

r2p 当前运营对象是 Rust/Python SDK 工程及其文档、版本和消费方。
目标是帮助开发者正确采用、降低构建和迁移成本、收集可复现反馈，并将高价值问题转化为需求。
上游 PyO3 的下载量、社区和站点不能计为本仓库独立业绩。

运营负责人管理用户触达与反馈，技术支持负责复现分类，产品负责人定优先级，开发/测试完成修复和验证，发行负责人交付版本。
本期使用 [r2p PR](https://github.com/jelven007/r2p/pulls) 接收复现/修复反馈，采用尽力维护政策；目标仓库 Issues 当前关闭。
实际团队人员、工作时间和合同响应目标在建立正式支持时明确。

## 3. 反馈闭环

反馈按[支持政策](support-policy.md)进入本仓库 PR；Issues 启用后再使用问题模板。
上游社区入口仅为第三方参考，不代替 r2p 问题接收。
提交者提供版本/SHA、Rust/Python、OS/架构、features、ABI/GIL、安装命令、最小复现及错误；日志先移除凭证和无关个人数据。

支持人员按构建/打包、导入/ABI、语义/转换、内存/并发、性能、文档、功能请求分类，去重关联原问题。
确认影响后分流到缺陷、需求、使用说明或环境排查；修复关联需求编号、PR/提交和回归结果。

状态流转：新建 → 待复现 → 已分类 → 已安排 → 修复/答复 → 用户验证 → 关闭。
不能复现的问题记录已尝试环境及缺失信息；超期问题按角色升级。
复发关联原记录，进入根因和预防措施。

具体故障分级及恢复见[运维手册](../runbooks/incident-response.md)。
响应与版本维护边界见[支持政策](support-policy.md)，当前没有响应时间承诺。

## 4. 指标定义

| 指标 | 计算口径 | 数据来源 | 使用方式 |
| --- | --- | --- | --- |
| 已验证采用数 | 统计周期内有登记版本和成功集成证据的消费项目数 | 自愿采用登记/发行记录 | 判断支持覆盖；不推算活跃用户 |
| 构建成功率 | 成功的独立构建任务 / 总任务；按平台版本分组 | 本仓库 CI/支持记录 | 发现平台或打包退化；重试单独标记 |
| 首次集成耗时 | 受支持环境首次尝试到成功导入的耗时分布 | 自愿试用记录 | 改进教程；区分下载等待与操作时间 |
| 首次有效响应时间 | 问题提交到给出复现/分类/解决建议的耗时 | Issue/支持记录 | 按严重级别报中位数和 P90 |
| 修复周期与积压 | 确认缺陷到验证交付；未关闭缺陷按严重级别和年龄统计 | 缺陷和发行关联 | 决定优先级，防止只统计已关闭项 |
| 升级/复发情况 | 升级成功样本、失败样本及同根因再次出现次数 | 消费方验证/事故记录 | 优化兼容测试与迁移材料 |
| 文档有效性 | 教程失效、缺页、命令失败和补充需求数量 | 文档问题/链接检查 | 维护与代码一致的材料 |

不在 SDK 中默认采集使用遥测。
采用登记需说明自愿性、字段、用途、权限和保留期。
发布下载数只有在取得本仓库真实注册表数据并解释缓存、镜像和机器人影响后才可报告。

## 5. 运营节奏

每个发行周期更新用户材料、兼容/已知问题、迁移路径和支持状态。
每周处理新问题、阻断缺陷和积压；每月审视分组指标、教程问题和复发根因，并产生需求/文档改进任务。

发行前向目标消费方提供明确候选版本和验证范围；发行后跟踪实际安装/导入与关键集成结果。
通知渠道、收件人和内容按发行负责人确认的范围执行。

## 6. 支持政策与退出

本期范围按[已测矩阵](../testing/support-matrix.md)解释；实验 async/inspect/WIP no_std 单独管理。
主分支及两个快照的维护策略见支持政策；正式版本支持期限、人员和值守窗口在 Q-04 扩展项确认。
停止支持须提前给出替代版本、迁移材料和最后修复版本。

运营交付物包括采用登记、问题分类与响应规则、月度指标、发行沟通材料和改进清单。
当前只有源码仓库和文档流程，不把尚未采集的指标填写为零或成功率 100%。
正式运营准入需要实际负责人与数据渠道。
