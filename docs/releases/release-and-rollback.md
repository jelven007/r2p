# r2p 发行、部署与回退方案

版本：2.0；日期：2026-10-24；状态：源码交付流程生效，注册表/站点交付待单独验收。
本次目标为 `jelven007/r2p` 的分支推送和主分支合并，具体证据记录在[源码交付记录](records/2026-10-24-production-baseline.md)。
关联：FR-007、NFR-003–NFR-007。

## 1. 发行身份与对象

产品名称已确认为 `r2p`，以 [product.toml](../../product.toml) 为准。
按[ADR-0002](../architecture/adr/0002-product-and-release-boundaries.md)采用固定 Git revision 的源码交付。
SDK 包名为 `r2p` / `r2p-*`；作者和许可保留原始来源。
源码仓库权限不代表 crates.io/PyPI 包和 `pyo3.rs` 站点权限。

发行对象包括 Rust crates、独立 Python 包/内省 wheel、用户文档和消费方集成说明。
`tests/python`、基准、FFI 校验工具及开发环境是工程资产，不作为 SDK 产品制品发行。

Rust 发布、PyPI 发布、Netlify 部署分别要求仓库变量 `R2P_ENABLE_CRATES_IO`、`R2P_ENABLE_PYPI`、`R2P_ENABLE_NETLIFY` 为 `true`。

## 3. 版本与兼容

源码消费固定主分支已合并的完整 SHA；版本和两个历史快照按[版本政策](version-policy.md)维护。
API/ABI、解释器/MSRV、宏诊断、特性和内省协议变化必须提供兼容说明。
实验能力的版本与支持声明单独列出。

同一发行单元中 `r2p-*` 精确版本依赖需协调更新；根清单、子 crate、towncrier、指南版本、示例和生成模板同步验证。
当前源码声明 `0.30.0` 不证明本仓库有同名注册表版本。

## 4. 准备与验证

源码交付执行：检查授权范围和工作区 → 本地验证 → 分支提交/推送 → PR → 检查结果分类 → 普通合并 → 核验远端 SHA 和两个历史标签。
源码交付须通过 G1、对应 G2/G3 与本地 MSRV；远端跨平台失败按源码/配置和平台资源分别记录。
实质代码失败修正后再合并；没有 Actions 运行证据时不得声称远端矩阵通过。
完整注册表交付使用以下步骤：

1. 确认发行身份、范围、目标平台及授权。
2. 固定源码和依赖解析，更新版本、CHANGELOG/newsfragments、兼容/迁移和已知问题。
3. 运行门禁，保存原始日志与摘要；生成完整制品清单。
4. 校验每个包的源码、README、许可证、编译 include 和依赖；测试路径不得影响安装包构建。
5. 在隔离环境安装候选 wheel/构建候选 crate，验证导入、关键 API、异常和消费方回归。
6. 指定旧版本/哈希与恢复步骤，完成演练并形成发行审阅记录。
7. 经发行决策后再执行远端交付，验证目标注册表/站点与版本可用性。

准备阶段可执行的本地命令：

```bash
git status --short --branch
cargo metadata --no-deps --format-version 1
cargo package -p r2p --list
python tools/check_repository.py
uv run --isolated --only-group nox nox -s build-guide
```

`cargo package --list` 只检查候选文件，不证明打包后编译成功。
当前精确版本依赖是否已在目标注册表可用需单独验证；必要时按已确定的内部注册表/本地候选包链路完成离线/隔离构建。
不能用跳过 package verification 代替发行验收。

## 5. 发布后核验

从目标注册表重新下载制品，核对名称、版本、哈希和平台/ABI，再在干净环境安装并验证。
抽查文档版本链接、迁移材料和已知问题。
目标消费方反馈关联实际制品和发行记录。

发行完成需保存：源码 SHA、审批人、包/站点地址、构建时间、工具链、依赖快照、测试报告、哈希、支持范围、监测和回退证据。
状态依次为候选 → 已批准 → 已交付 → 已核验，失败进入暂停/撤回，不跳过核验状态。

## 6. 停止与回退

触发条件：不可导入、ABI/标签错误、关键语义或内存回归、缺失/错误制品、站点版本错误，以及必需矩阵未通过。
发行负责人停止后续交付，运维确认影响，支持协调已授权的消费方反馈。

| 目标 | 恢复动作 | 必需验证 |
| --- | --- | --- |
| Git 源码/消费方 | 检出历史快照或通过 revert PR 恢复，固定 Git SHA，重新解析/构建 | 依赖版本、名称迁移、编译和关键消费场景 |
| Python 消费方 | 安装保存的旧 wheel/哈希并清理受影响环境 | 导入、平台/ABI、关键 API 和业务回归 |
| 注册表 | 按平台能力 yank/撤回问题版本，保留记录并发布新修复版本 | 可见性和消费方选择；旧版本不可假定被远程删除 |
| 文档站点 | 恢复上一份已验证静态制品及对应路由 | 版本入口、页面、链接和目标域名 |
| 流水线配置 | 恢复已验证配置/工具链并重跑候选验证 | 目标、授权、路径和制品正确 |

不得移动已被消费的发行标签或覆写同一版本制品来掩盖失败。
已经安装的制品不能通过注册表撤回自动恢复；消费方需要执行安装/重建。
修复以新版本交付并补充迁移与事故记录。

## 7. 退出条件

源码交付以远端合并 SHA 可获取、两个标签 SHA 一致、本地 main 与远端一致且工作区干净关闭。
外部发行以 G5/G6 通过、目标制品重新获取成功、关键消费场景和站点核验成功、支持与恢复责任明确关闭。
失败发行保留完整时间线、影响、停止原因和后续动作，模板见[变更与发布记录](../governance/change-record-template.md)。
