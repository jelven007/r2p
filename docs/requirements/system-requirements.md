# r2p 系统需求规格

版本：1.0；日期：2026-10-24。
状态：生产研发拟定基线，业务范围和对外承诺待负责人确认。
产品名称 `r2p` 已确认，元数据见 [product.toml](../../product.toml)。
源码版本见[项目分析](../governance/project-assessment.md)。

## 1. 目标与范围

建立可持续维护的 Rust/Python 互操作 SDK 工程，使新增功能具备清晰的需求、方案、代码、测试和交付证据。
继承上游 PyO3 的技术能力，明确本仓库的产品和运维责任。

首期范围：SDK、安全对象层、FFI、宏、构建配置、兼容矩阵、测试、示例、性能、内省工具、文档和交付流程。
业务 HTTP 服务、数据库模型、管理后台、租户认证及支付不在已定义需求中；新增时需单独立项并补充部署和数据需求。

## 2. 用户与使用场景

| 用户 | 输入/操作 | 预期结果 |
| --- | --- | --- |
| Python 开发者 | 使用 maturin 等打包 Rust 函数/类 | 可导入扩展，返回值和异常符合 Python 契约 |
| Rust 开发者 | 初始化并附着解释器，调用 Python 对象 | 返回 Rust 类型，生命周期/线程约束明确 |
| 打包维护者 | 选择解释器、目标平台和 ABI | 得到可安装、可验证、可追溯的制品 |
| 库维护者 | 修改宏、FFI、转换或兼容配置 | 回归、诊断和文档同时更新 |
| 支持/运维人员 | 处理导入、崩溃、性能或构建问题 | 可复现、定级、定位、恢复并反馈需求 |

## 3. 功能需求

P0 表示稳定交付必须满足；P1 表示受控推进的能力。
现有能力状态不代表生产验收通过。

| 编号 | 优先级 | 需求和契约 | 可观察的验收条件 | 当前能力 |
| --- | --- | --- | --- | --- |
| FR-001 | P0 | Python 能调用 Rust 函数/类/模块 | 构建扩展后能导入；正常、边界参数、非法类型及类方法测试通过 | 已实现 |
| FR-002 | P0 | Rust 能嵌入并调用 Python | 初始化策略显式；附着、对象调用、异常与解释器生命周期测试通过 | 已实现 |
| FR-003 | P0 | 类型转换与异常保持语言语义 | `FromPyObject` / `IntoPyObject` 往返测试通过；错误带类型与上下文；引用释放符合契约 | 已实现 |
| FR-004 | P0 | 宏生成入口可用且诊断可回归 | 支持声明宏和 derive；非法签名等产生预期编译诊断，UI 测试通过 | 已实现 |
| FR-005 | P0 | 支持声明的平台/解释器/ABI 组合 | 维护已测矩阵；支持清单每项有构建与运行证据；不支持组合有明确说明 | 已实现部分，生产矩阵待验收 |
| FR-006 | P1 | 内省与类型 stub 生成可受控使用 | 支持对应二进制格式；stub 与实际模块一致；协议不兼容时报错；实验标识明确 | 实验能力已实现 |
| FR-007 | P0 | 交付可安装和可追溯的制品 | 记录源码 SHA、版本、工具链、平台、ABI、依赖和校验和；隔离环境安装/导入成功 | 工具已存在，独立交付待完成 |
| FR-008 | P0 | 研发资料和目录保持一致 | 本地目录、Cargo/Nox/CI/mdBook 路径有效；文档覆盖全生命周期并能追踪到实现/验收 | 本次落地 |

## 4. 非功能需求

| 编号 | 优先级 | 要求 | 验收标准与测量方式 |
| --- | --- | --- | --- |
| NFR-001 | P0 | 内存、借用与线程安全 | 关键 unsafe 变更说明不变量；引用、GC、初始化并发及线程借用回归通过；验证有 GIL 与 free-threaded 条件 |
| NFR-002 | P1 | 性能可比较 | 同硬件、工具链、解释器、ABI、特性和 release 优化下至少 3 次测量；核心基准中位数退化超过 5% 触发分析和负责人决策，阈值为拟定门槛 |
| NFR-003 | P0 | 兼容性可治理 | API/ABI/特性变更有兼容分析和迁移说明；MSRV 与支持矩阵一致；实验功能不得默认提升为稳定承诺 |
| NFR-004 | P0 | 构建和来源可追溯 | 发布记录包含依赖锁定快照、构建工具版本、源码 SHA、制品哈希和许可证；凭证仅由环境/注册表授权提供 |
| NFR-005 | P0 | 测试门禁可执行 | P0 用例必过；稳定工具链必需检查成功；失败和跳过均有原因；本地验证与跨平台 CI 结果分别记录 |
| NFR-006 | P0 | 文档完整并及时更新 | 需求→方案→实现→测试→发行记录可追踪；代码变更同时更新受影响文档；本地链接/路径检查通过 |
| NFR-007 | P0 | 可诊断、停止与恢复 | 发布前演练制品降级/站点恢复；失败发行不能复用原版本号；事故记录含影响、时间线、证据和后续动作 |
| NFR-008 | P1 | 使用反馈与支持形成闭环 | 建立问题分类、去重、优先级和响应角色；按版本/月统计采用、构建失败、问题响应和复发情况；指标口径可解释 |

项目是基础库，服务 uptime、请求 QPS、数据库 RPO 等不能直接套用。
文档站点、发布流水线和采用 SDK 的业务服务分别定义自己的 SLI/SLO。

## 5. 公共契约和数据

接口是 Rust 公共 API、Python 导出对象、FFI ABI 和内省格式；详见[接口与兼容性](../architecture/interfaces-and-compatibility.md)。
SDK 不持久化业务数据。

工程数据包括源码 SHA、需求编号、测试结果、特性组合、解释器版本、构建日志、制品哈希、发行和问题记录。
所有运行证据应至少带：版本/SHA、操作系统与架构、Rust/Python 版本、GIL/ABI 模式、特性、命令和结果。

## 6. 验收门禁

| 门禁 | 范围 | 必需证据 |
| --- | --- | --- |
| G1 | 仓库与文档 | 工作区和独立工具 metadata；路径检查；格式与文档检查 |
| G2 | Rust 行为 | 主库/组件单元测试、集成/UI/doctest；声明特性组合 |
| G3 | 跨语言 | Python 扩展安装与 pytest；示例、异常、stub 测试 |
| G4 | 兼容与性能 | MSRV、稳定版本、平台/解释器/ABI 矩阵；基准比较 |
| G5 | 发行 | 身份/权限确认；版本、包内容、哈希；隔离安装与导入；发行记录 |
| G6 | 支持与恢复 | 责任分配；支持策略；告警/事故路径；回退演练记录 |

本次目录/文档变更按 G1、相关 G2/G3 进行验证；G4–G6 仍是生产发行前的完整准入条件。
具体执行结果以[验证报告](../testing/validation-report.md)为准。

## 7. 优先级和变更控制

需求状态流转：拟定 → 已确认 → 实现中 → 待验收 → 已验收 → 维护/废弃。
每次变化记录原因、影响、负责人和证据；能力存在与需求验收使用两个独立字段。

追踪关系使用[traceability.csv](traceability.csv)。
变更需求先评估 API/ABI、Python/Rust 版本、特性、平台、文档和运营影响，再更新追踪矩阵和测试计划。
